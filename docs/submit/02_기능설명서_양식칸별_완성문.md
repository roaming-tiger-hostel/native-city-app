## B. 서비스 기획 배경 및 필요성
외국인·국내 여행자 모두 “리뷰는 많은데 누구 취향을 믿어야 할지” 모르는 문제가 있다. 불특정 평점보다 **특정 네이티브/호스트의 취향으로 추천**받는 대화형 경험이 필요하고, 장소 사실은 한국관광공사 OpenAPI로 근거를 남겨야 한다.

## C. 서비스 개요
### C-1. 한 줄 소개
서울 여행자가 문화·식사 제약·취향에 맞는 AI 친구와 대화하며, TourAPI(서울 전역 핫스팟) 장소를 근거로 추천받는 웹 서비스.

### C-2. 주요 기능
1. 게스트(`/guest`): 18세그먼트 칩 → 캐릭터·제약 → **JEV**가 골든카드·답 칩·장소 옵션을 턴마다 선택 → 지도·출처. 카드 미스·구 키워드·「다른 데」는 Qwen/규칙 엔진이 왜·가는법·주의로 자세히 답함(가짜 영업시간 금지).
2. 문화·여행 프리셋(할랄·채식·예산·K-pop 등)과 기본 친구 세트
3. 호스트(`/studio`): 취향 A/B·TourAPI 장소 동기화
4. 심사(`/submit`): TourAPI·LLM 설정 상태

### C-3. 차별성
불특정 리뷰 절대값이 아니라 **“누구의 취향으로 추천받느냐”**. 추천은 캐릭터/호스트에 귀속되고, 장소 명칭·주소·좌표는 공사 OpenAPI를 근거로 표시한다. 골든카드로 빠른 답을, 미스 시 LLM/엔진으로 상세 답을 나눈다.

### C-4. 지역 범위
1차 데모는 **서울 전역**. TourAPI `locationBasedList2`를 성수·을지로·광장·한남·홍대·강남·명동·잠실 등 핫스팟에 멀티 호출한다. 호스텔 반경만 고집하지 않으며, 「가까움」칩일 때만 거리 가중을 강하게 둔다. 전국 확장은 이후 과제. (공고상 지역특화=서울제외 → 해당없음)

## D. 한국관광공사 OpenAPI 활용
### D-1. 활용 서비스
국문 관광정보서비스_GW (KorService2). EngService2 병행. JpnService2는 미신청(403).

### D-2. 활용 방식(메서드)
| 메서드 | 화면/API | 쓰는 정보 |
| --- | --- | --- |
| locationBasedList2 | `/api/tour`, `/api/chat`, 지도 | **서울 핫스팟 멀티 쿼리** — 음식점·관광지 명칭/주소/좌표/이미지 |
| searchKeyword2 | 채팅 구·지역 요청(강남/홍대/명동 등), 스튜디오 검색 | 검색 후보 |
| detailCommon2 | `/api/tour?contentId=` | 개요·연락처·좌표 |

실시간 호출 실패 시 데모 시드 폴백. 시드만으로는 공사 호출 성공 증빙이 아니다. 할랄 인증·실시간 영업 여부는 TourAPI에 없으면 지어내지 않는다.

### 3분 시나리오
1) `/guest` 18세그먼트·캐릭터 → 칩/채팅 → 장소 카드 → 지도·출처
2) 「강남 맛집」「홍대 카페」「명동」등 구 키워드 → 해당권 TourAPI 후보
3) 「다른 데」→ 세션 place 제외 후 엔진/Qwen
4) `/submit`에서 TourAPI 라이브 로그 확인

## F. 발전 방향
단기: 답 품질·호스트 학습 루프·TourAPI 근거 강화. 중기: 더 많은 문화권 친구, 호스텔 연동 커머스/투어 대행.

## G. 현재 제약(정직)
프로덕션 LLM 키 없으면 규칙 엔진/폴백으로도 데모 가능. 영구 DB·실인증·요청량 제한은 데모 단계. 민감정보 입력 금지.
