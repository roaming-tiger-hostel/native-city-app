## 0. 출발점 — 이미 한 번 실패했다

2026-01~02에 rollinjoint 자동화에서 같은 문제를 건드렸고 실패했다. 그 흔적이 파일로 남아 있다.

**증거**: `~/projects/rollinjoint-auto/data/references/_analysis.json` (2026-01-29)
대본 4개(`Shan_SHui_Social`, `Cafe_Seek__Day_40_`, `golden_pheonix`, `sample-2`)에서 자동 추출한 스타일 가이드. 내용은 톤, 훅 패턴(`"People say X, but that's only cause they haven't followed me, rollinjoint"`), 어휘, 페이싱, 스토리텔링 기법. **잘 뽑혔다.**

그런데 **"무엇을 좋은 집이라고 보는가"는 한 줄도 없다.**

**형의 피드백** ([reference/rollinjoint/00-process-analysis.md](../reference/rollinjoint/00-process-analysis.md) §3):
> "이론적으로는 흥미를 유발할 수 있지만, 사실상 너무 지루한 것들을 말한다"
> — 너무 generic함. 형이 반영하려는 **현실**을 AI가 모름. 구체적 디테일을 못 잡음.
> 예: "포크가 없는 중국식당", "8가지 고추를 씀"

**진단**: 스타일 문제가 아니다. "포크가 없다"가 *왜 언급할 가치가 있는 디테일인지*는 형이 **무엇을 진정성의 신호로 보는가**를 알아야 나온다. 스타일 가이드는 *어떻게* 말할지는 알려주지만 *뭘 말할 가치가 있는지*는 못 알려준다. **추출 대상을 잘못 잡았다.**

전략 §5의 경고 — *"추출 안 된 채 출시 = 형 이름 단 제네릭 답 = 최악"* — 이 이미 한 번 실현됐던 것.

**부수 사실**: 그때 next steps 첫 줄 `[ ] 형한테 과거 잘된 스크립트 5-10개 확보`가 6개월째 미체크. 문서엔 "기존 대본 ~100개 있음"이라 적혀 있으나 그건 형 인스타에 있다는 뜻이고, 우리가 확보한 건 4개뿐. **시드 확보 자체가 아직 안 된 상태.**

## 1. 리프레임 세 개

### 1-1. 추출 대상은 말투가 아니라 판정 기준

"취향" 한 단어에 세 가지가 섞여 있다:

| | 무엇 | 현재 상태 |
|---|---|---|
| **선택 (selection)** | 어디를 갈지/소개할지 고르는 기준 | 손도 안 댐 |
| **판정 (judgment)** | 간 곳을 어떻게 평가하나 — 뭐가 진짜고 뭐가 관광객용인가 | 손도 안 댐 |
| **서술 (articulation)** | 왜 좋은지 말하는 방식 | `_style_guide.md`, `_analysis.json`에 있음 |

서술은 선택·판정에 **의존**한다. 서술만 뽑으면 제네릭한 내용을 형 말투로 말하는 물건이 나온다 (= 2026-02에 실제로 나온 것).

→ **뽑아야 하는 건 판정.**

### 1-2. 전체가 아니라 델타

형의 취향 전체를 뽑으려 하면 안 된다. 상당 부분은 프런티어 모델이 이미 안다 — "손으로 만든 게 공장 것보다 낫다", "30년 된 집엔 이유가 있다". 아키텍처 §7-3의 *"대화 바닥선은 프런티어가 거의 공짜로 준다"* 를 **판정**에도 그대로 적용한다.

→ 뽑을 건 **컨센서스와 형이 갈리는 지점(델타)뿐.**

이유:
- 일치하는 데이터는 정보량 0 → 라벨 낭비
- 델타가 정확히 차별화 = **해자 그 자체**
- 전체보다 **훨씬 작다** → 형의 적은 시간으로 커버 가능. 아키텍처 §4-4의 *"인플루언서 채점은 품질 최고지만 양이 적음"* 문제를 우회
- **측정 가능하다** → D3(eval 루브릭)이 딸려 나옴

### 1-3. 형의 취향은 user profile이 아니라 scoring function

아키텍처 §6-2 보정이 필요한 지점.

§6-2는 *"넷플릭스·스포티파이가 협업 필터링으로 푸는데 RLHF가 왜 필요하냐"* 고 했고 이건 **게스트 취향**에 대해서는 맞다 — 게스트는 몇 번 인터랙션이면 저차원 공간에 위치시킬 수 있다.

그런데 **형의 취향은 유저 프로필이 아니라 아이템 스코어링 함수 자체**다. 형은 1인 평가자이고, 평생 판정한 가게가 수백 곳, 그것도 대부분 런던이다. 넷플릭스의 조건(고정 카탈로그 + 수백만 유저 행동)의 **정반대 — tiny-N, 단일 전문가, 콜드스타트.**

→ "추천 시스템으로 풀면 된다"가 그대로는 안 먹힌다. **게스트 축과 형 축을 분리해 각각 다른 방법으로 푼다.**

## 2. 설계안 — 루브릭을 1급 산출물로

**핵심**: 산출물은 모델 가중치도 few-shot 뭉치도 아니고, **형이 읽고 고칠 수 있는 루브릭 문서 + 축별 가중치**.

### 추출 루프

```
0. 커버리지 정의   후보 집합 확정 (지역 × 카테고리, N개)
1. 루브릭 초안     형의 과거 산출물에서 역추출 —
                  "왜 이 집을 골랐나, 무엇을 진짜의 신호로 봤나"
                  ← 형이 쓰는 게 아니라 뽑아내는 것
2. 반박            형에게 초안을 보여주고 틀린 데를 고치게 함
                  ← introspection을 쓰는 유일한 지점.
                    백지보다 반박이 훨씬 쉽다 ("이건 아니야"는 사람이 잘함)
3. 델타 채굴       후보 쌍을 프런티어에 먼저 판정시키고,
                  헷갈리거나 축끼리 충돌하는 쌍만 형에게 A/B로
4. 이유 캡처       고를 때 한 줄 이유를 음성으로
                  ← 타이핑 시키면 안 함. 음성 dumping은 이미 형의 습관
                    (process-analysis §2)
5. 갱신            선택 + 이유 → 루브릭에 축/예외 추가
6. eval            홀드아웃 쌍 예측 정확도, 프런티어 베이스라인 대비
                  → 임계 넘으면 투입, 아니면 3으로
```

### 엔진 형태 (하이브리드)

- **축 정의** = 자연어 루브릭
- **후보의 축별 점수** = LLM이 1회 매겨 캐시
- **축 가중치** = 형의 A/B 선택에서 **Bradley-Terry**로 학습

축이 10개 내외면 **100~300쌍에 수렴**. 새 후보는 축 점수만 매기면 랭킹이 나온다. 캐릭터 LLM은 그 랭킹 + 이유를 받아 말로 엮는다 — 아키텍처 §6-2의 *"뭘 추천하나는 추천 엔진이 풀고, LLM은 그 결과 + 사실(RAG) + 프로필을 받아 말로 엮는 역할"* 그대로.

### 왜 루브릭이 1급이어야 하나

- 형이 검수 가능 → 신뢰
- 새 도시·새 후보로 일반화 (커버리지 확장)
- 모델 갈아타도 살아남음
- **C2(IP·권리 배분)에서 자산 경계가 명확**해짐
- **eval 루브릭과 같은 물건** → D3 동시 해결

아키텍처 §8-1이 *"지식은 가중치 밖(검색)에 둔다"* 고 한 것과 같은 정신 — **취향도 가중치 밖(루브릭)에 둔다.**

### 형에게 물어보면 안 되는 것

**"네 취향이 뭐야?"** 사람은 자기 판정 기준을 introspect 못 한다 (아키텍처 §6-2가 캐릭터 챗 취향을 "암묵적·설명 불가"라 한 것과 같은 이유). 판정 *행위*를 시켜서 역추정해야 한다.

형 시간이 가장 비싼 자원이므로 **아무 쌍이나 물으면 안 되고, 모델이 가장 헷갈리는 쌍만** 묻는다 (active learning). 하루 10~20쌍, 30초짜리.

## 3. 새 논점 — 커버리지 경계

**문서 두 개 어디에도 없던 논점.**

형 자산은 **런던의 동양 음식**이다. Native City는 **방한 외국인 대상 한국**이고, 형의 한국 커버리지는 "가끔 방문"이라 얇다 (process-analysis 배경).

제네릭 답보다 나쁜 게 있다: **형이 안 가본 곳에 대해 형 이름으로 답하는 것.**

→ 답 모드를 셋으로 가른다:

| 모드 | 조건 | 표시 |
|---|---|---|
| **직접 판정** | 형이 실제 감 | "형이 갔다" |
| **일반화 판정** | 형의 루브릭을 새 후보에 적용 | "형이라면 여길 고를 것"으로 **명시 라벨링** |
| **모름** | 커버리지 밖 | 거절하거나 사실만 |

전략 §4 신뢰 규칙의 **대칭**이 필요하다:
- 기존: *"검증은 '사실'은 덮어쓰되 '취향'은 절대 못 덮어쓴다"*
- 추가: **"취향은 커버리지 안에서만 주장한다"**

## 4. 형 말고 나부터 (리허설)

형은 20만 팔로워고 시간이 비싸고, 실패하면 관계가 상한다. 반면 **나는 호스텔 1년 운영하며 신당·무학동 일대 판정을 이미 갖고 있다.**

내가 첫 번째 판정자가 되어 루프를 한 바퀴 돌리면:
- 형 시간 0, 관계 리스크 0, 반복 즉시 가능
- 루브릭 추출 → A/B → 가중치 학습 → eval 파이프라인이 **실제로 도는지** 검증됨
- 그 결과물이 **그대로 v1 호스텔 컨시어지의 시드**가 됨 (A2와 맞물림)

전략 §11의 *"엔진이 내 노드에서 돌기 전에 마켓플레이스부터 짓지 말 것"* — 같은 원칙을 데이터에 적용.

## 5. 실패 조건 (미리 정해둠)

판정자의 A/B 선택이 **어떤 축 조합으로도 예측이 안 되면** — 즉 홀드아웃 정확도가 프런티어 베이스라인 대비 유의미하게 안 오르면 — 그 취향은 저차원 구조가 아니라는 뜻이고 **이 해자 가설이 틀린 것**이다.

전략 §5가 걱정한 "추출 난이도의 반감기"보다 더 근본적인 문제. **일찍 아는 게 이득** — 6개월 태우기 전에.
