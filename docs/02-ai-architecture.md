# AI 캐릭터/컨시어지 모델 설계 노트

— 제타(Zeta) 분석에서 출발해 "여행 동반자형 AI(네이티브 시티)"의 아키텍처까지

> **이 문서의 목적** 대화에서 다룬 기술적 개념(RLHF·DPO·추천 시스템·그라운딩 등)과 예시를 한곳에 모아, ① 약했던 개념을 나중에 다시 공부하고, ② 옆으로 새 생각을 뻗을 때 베이스로 쓰고, ③ 더 다듬은 v2 문서를 만들 수 있게 정리한 작업용 노트.

---

## 0. 한 줄 결론 (TL;DR)

- 제타와의 격차는 "모델을 직접 만든다"가 아니라 **"데이터 + 반복 루프"**에 있다. 베이스 모델은 이제 병목이 아니다.
- 솔로/소규모는 자체 모델 학습 싸움을 피하고, **강한 베이스(API) + 오케스트레이션 + 데이터**로 가는 게 압도적으로 유리하다.
- 네이티브 시티의 해자는 "대화 선호량(제타식)"이 아니라 **"행동·관심사·문화권 데이터"**다. 종류가 다른 데이터라 제타 규모의 유저가 전제 조건이 아니다.
- **"동반자형 유대감"은 제타와 종류가 다르다.** 제타는 그라운딩 없는 롤플레이라 RLHF로 미감을 구워야 하지만, 네이티브 시티의 유대감은 "이 사람이 사랑하는 구체적 사실을 안다"는 적중에서 나온다 → 데이터·검색의 문제.
- **한 캐릭터 = (공유 베이스가 주는) 감성 바닥 + (얇은) 페르소나 층 + (가중치 밖) 지식·검색 층.** 이 셋을 분리해서 각자 맞는 방법으로 다룬다.

## 1. 제타(Zeta)는 구조적으로 어떻게 만들어졌나

> 출처: 스캐터랩 기술 블로그(blog.scatterlab.co.kr), AI타임스 보도, 엘리스클라우드 케이스 스터디, 나무위키. (세부 스펙 상당수는 비공개라 추정 포함.)

### 1-1. 내부 모델 — 외부 API가 아니라 자체 학습 모델

- 개발사: **스캐터랩**(이루다·강다온 등 감성 챗봇 계보).
- 외부 LLM API(OpenAI/Gemini)를 쓰지 않고 자체 sLM **"스팟라이트(Spotwrite)"** 를 직접 학습해 사용.
  - 계보: 초기엔 감성 대화 특화 모델 **핑퐁1(pingpong1)** 에 스토리 중심 미세조정 → 이후 스팟라이트로 발전 → 최신 **스팟라이트 V3**(2025.12, 기억력·답변 품질 개선).
  - 학습 방식: 맞춤 데이터셋 기반 **파인튜닝 + 강화학습(RL)**.
  - 규모: 파라미터 비공개, **30B(300억) 미만 sLM**으로 추정.
  - 인프라: AWS **H100 8노드(64 GPU)** 학습, 최근 B200 클러스터 분산 학습 성능 검증.

### 1-2. 모델 티어 / 기억력

- 유저가 모델을 고를 수 있고(zeta / koji 등), 티어마다 컨텍스트·기억 유지력이 다름.
- 체감: zeta ≈ 5턴, koji ≈ 15~20턴 수준이라는 유저 보고.
- **기억력은 모델만의 문제가 아니라 주변 파이프라인이 큼.**

### 1-3. 오케스트레이션 레이어 (체감 품질의 핵심)

- **요약(summarization)**: 긴 스토리를 중간중간 요약해 다시 모델에 주입 → 장기 문맥 유지.
- **로어북(lorebook)**: 키워드 등장 시 관련 설정을 호출 → 사실상 경량 RAG.
- **지시문 시스템 / 유저 프로필**: 캐릭터 톤·관계·배경을 조건으로 주입.

### 1-4. 내부 구현을 "확인하는 방법"

- **1차 공식 소스**: 스캐터랩 기술 블로그(ML 리서처 인터뷰), 보도자료, 인프라 파트너 케이스 스터디(GPU 구성·배치 사이즈 같은 디테일이 의외로 노출됨).
- **앱 내부 단서**: 모델 선택 UI의 라벨(zeta/koji) = 그들이 운영하는 모델 티어.
- **블랙박스 프로빙**: 동일 프롬프트를 모델별로 던져 토큰 길이·거부 패턴·컨텍스트 한계·지연을 비교 → 규모/윈도우 역추정.
- **네트워크 트래픽 분석**: mitmproxy 등으로 페이로드 관찰(외부 API 호출 여부 정도는 보임). 단, **약관 위반·법적 리스크 있어 권장하지 않음.**

## 2. 캐릭터 챗 모델을 만드는 난이도 — 4개 층

> 핵심: 층이 올라갈수록 "혼자"에서 "팀+데이터+클러스터"로 넘어간다. 그런데 체감 품질의 대부분은 1~2층에서 나온다.

| 층 | 내용 | 누가/얼마나 | 비고 |
|---|---|---|---|
| **1층. 오케스트레이션** | 프롬프트 엔지니어링 + 요약 기반 컨텍스트 관리 + 로어북식 키워드 검색 (경량 RAG) | 솔로, 며칠~몇 주 | 체감 품질의 **70~80%가 여기서** 나옴. 제타의 "캐릭터 일관성·기억력" 상당수가 모델이 아니라 이 층. |
| **2층. SFT 파인튜닝** | Gemma/Qwen에 LoRA/QLoRA로 캐릭터 대화 수천~수만 건 학습 (말투·포맷·지시문 준수 안정화) | 솔로지만 진지하게, 몇 주~몇 달 | 빌린 24~48GB GPU 1장이면 충분. 추론은 맥미니에서 양자화로. |
| **3층. DPO/RLHF + 평가 인프라** | 선호 데이터로 강화학습 + eval harness | 소규모 팀/예산 | 어려운 건 학습 코드가 아니라 **선호 데이터 라벨링 파이프라인**. |
| **4층. (대규모) 프리트레이닝** | H100·B200 클러스터, 매주 모델 배포, ML 연구 조직 | 솔로 불가 | 굳이 갈 이유도 거의 없음. |

**리프레임**: 격차의 본질은 아키텍처가 아니라 **데이터 + 반복 루프 + 서빙**. 솔로라면 자체 모델 학습에 힘 빼는 대신 강한 베이스(API 또는 파인튜닝한 오픈모델) + 1~2층 오케스트레이션 + 데이터 수집 루프가 정답. 참고로 요즘 제타는 모델 성능 자체로는 상위권이 아니라서(자체 모델 검열·정체), 프런티어 API + 좋은 오케스트레이션이면 채팅 품질로 제타를 넘는 것도 비현실적이지 않음. **못 따라가는 건 품질이 아니라 비용 구조와 데이터 스케일.**

## 3. "데이터를 쌓는다"의 정체 — '정답지'는 사실 3종류

"정답지"라는 한 단어 안에 서로 다른 데이터가 섞여 있다. 어느 걸 만드느냐가 무엇을 할 수 있는지를 가른다.

1. **시연 데이터 (SFT용 정답지)** — "이 상황에서 이 캐릭터는 이렇게 답해야 한다"는 *모범답안 하나*. → 파인튜닝(2층)의 연료.
2. **선호 데이터 (DPO/RLHF용)** — 정답 하나가 아니라 "A가 B보다 낫다"는 *비교/순위*. → 강화학습(3층)이 먹는 데이터.
3. **평가셋 (eval rubric)** — 학습이 아니라 "지금 모델이 얼마나 잘하나"를 *채점*하는 기준표. (의외로 가장 먼저 필요. 측정 없이는 개선 못 함.)

> **같은 데이터, 다른 손잡이** 똑같은 (상황, 응답 A) 쌍 하나를 → ① few-shot 예시(in-context), ② SFT 모범답안(모방 학습), ③ DPO의 "선호된 절반"으로 쓸 수 있다. 쓰는 방법에 따라 의미가 완전히 달라진다.

**인플루언서 라벨링이 어디로 가나**: 직접 이상답을 쓰게 하면 SFT, 두 후보 중 고르게 하면 선호 데이터, 모델 출력을 승인/반려하게 하면 둘 다 동시에 나옴. (= 호스텔에서 이미 하는 "AI 초안 → 사람 승인" human-in-the-loop과 같은 패턴.)

## 4. RLHF와 DPO의 원리 (1차원리부터)

### 4-1. 가장 중요한 구분 — 세 가지 메커니즘

| 메커니즘 | 응답 A가 어디에 사나 | 가중치 | 성격 |
|---|---|---|---|
| **In-context (few-shot / RAG)** | 추론 때 프롬프트 안 | 안 변함 | 휘발성. 그때그때 참고. |
| **가중치 업데이트 (SFT / DPO / RLHF)** | 학습에 쓰고 버려도 됨 | **변함** | 영구. 패턴이 가중치에 내재화. |
| **검색/암기 (retrieval)** | 저장해뒀다 꺼내 재생 | 안 변함 | 사실 저장·재생. |

> **핵심 깨달음**: DPO/RLHF에서 "선호된 응답 A"는 저장해서 똑같이 재생하는 것도, few-shot으로 쓰는 것도 아니다. 모델한테 "이런 결의 응답은 확률을 높이고 B 같은 건 낮춰라"라고 **가중치를 미세하게 밀어주는 것**. → 모델은 A를 통째로 외우는 게 아니라 **A가 가진 '결'을 내재화**하고, 한 번도 본 적 없는 새 상황에도 그 결대로 일반화한다. 이 **"일반화"가 암기·검색과 RL을 가르는 결정적 지점.**

### 4-2. 클래식 RLHF (보상모델 + PPO)

1. 사람이 선호 데이터 수집 (A > B).
2. 그 데이터로 **보상모델(reward model)** 학습 = 임의 응답에 점수를 매기는 *자동 채점관*. (사람 채점 기준을 내재화)
3. 본체 모델을 RL(**PPO**)로 학습: 본체가 답 뽑으면 채점관이 점수 주고, 높은 점수 쪽으로 가중치가 밀림.
4. **포인트**: 보상모델이 사람이 본 적 없는 새 상황에도 점수를 줌 → 채점 몇 천 건이 무한히 많은 상황으로 일반화된다.

### 4-3. DPO (Direct Preference Optimization)

- 보상모델도 PPO 루프도 **건너뜀.** 같은 선호 쌍(A > B)을 받아 본체 모델을 직접 한 번의 supervised 스타일 학습으로 민다.
- 수학적으로 RLHF 목표와 거의 등가인데 **훨씬 단순·안정적, 적은 컴퓨트.**
- 솔로/소규모는 거의 무조건 **DPO** (PPO는 튜닝 지옥). 변종: KTO, ORPO, IPO.

### 4-4. "왜 우리가 모자라나" = 방법이 아니라 양 + 신호 소스

- **양**: 선호 쌍이 충분히 많고 다양한 상황을 커버해야 일반화됨. 인플루언서 채점은 품질 최고지만 양이 적음.
- **신호 소스**: 제타가 강한 건 사람이 일일이 채점해서가 아니라 **손님 본인의 암묵 신호를 대규모로 긁어서**임.
  - 암묵 신호 예: regenerate를 눌렀나 / 대화를 이어갔나 / 세션이 길었나 / 좋아요를 눌렀나.
- **실전 루프 = 인플루언서 채점(고품질 시드/캘리브레이션) + 손님 암묵 신호(볼륨 엔진) 의 겹침.**

> **동전 비유**: 암묵 신호는 노이즈가 심하고 희소하다. "regenerate 한 번"은 동전 한 번 던진 것 — 답이 나빠서인지 그냥 다른 버전이 궁금해서인지 모호하다. 수천~수백만 번 던져야 미세한 편향(선호)이 보인다. 제타는 하루에 수백만 번 던지니 노이즈가 평균으로 씻겨나간다.

## 5. 규모 문제 다시 보기 — "유저가 많아져야만 되나?"

- **벽이 아니다. "임계점 + 시간" 문제다.** 유저가 충분히 늘면 같은 신호를 모을 수 있다.
- 제타의 우위 = 루다 때부터 쌓은 **"던진 횟수"의 헤드스타트**이지 영구 해자가 아니다.
- **유저 없이 부트스트랩하는 법:**
  - **RLAIF (RL from AI Feedback)**: 강한 프런티어 모델한테 후보 응답을 여러 개 뽑게 하고 채점까지 시켜 **선호 쌍을 합성**. 사람 취향이 꼭 필요한 축만 인플루언서 시드로.
  - 공개 선호 데이터셋(일반 helpfulness)로 베이스 보강.
- **진짜 해자 = 도메인·행동 데이터.** 대화 선호 신호와 달리 **인터랙션당 정보 밀도가 높아** 유저가 수백만이 아니어도 의미 있게 쌓인다. (KTO 데이터 공모전 때부터 본 "게스트 행동 데이터가 차별점"이 정확히 이 지점.)

## 6. "취향엔 정답이 없다" — 맞다, 그런데 RLHF가 답은 아니다

### 6-1. 컨시어지 응답의 두 층

- **사실·제약 층 (객관)**: 가게 영업 여부, 위치, 예산/할랄/거리 같은 하드 조건 → RAG·데이터 신선도. 틀리면 그냥 실패. (개념적으론 쉽지만 "최신성 유지 운영"은 많은 서비스가 죽는 자리.)
- **취향·핏 층 (주관)**: 사실이 다 맞다는 전제 하에 *이 사람에게 뭘 줄까*. (깔끔한 데 vs 을지로 노포)

### 6-2. 핵심 — 컨시어지 취향 ≠ 캐릭터 챗 취향 (종류가 다름)

| | 캐릭터 챗 취향 | 컨시어지 취향 |
|---|---|---|
| **성격** | 암묵적·설명 불가 (좋은 캐릭터 답이 뭔지 스펙으로 못 적음) | 명시적·구조화 (음식/가격/분위기/거리 축) |
| **학습 방법** | 수백만 암묵 신호에서 암묵 학습 → RLHF | 프로필 + 검색/랭킹 → 추천 시스템 |
| **데이터 효율** | 낮음(대규모 필요) | 높음(소수 인터랙션으로 사용자 위치 파악) |

> **"주관적 취향" ≠ "RLHF 필요".** 넷플릭스·스포티파이·옐프가 전부 주관적 취향을 다루지만 LLM에 RLHF를 돌려서가 아니라 **협업 필터링 + 콘텐츠 피처 + 선호 프로필**로 푼다. 이유: 취향이 **저차원 구조화 공간**에 살아서, 사용자를 그 공간에 위치시키는 데 인터랙션 몇 번이면 충분. (캐릭터 챗의 "좋은 답"은 거대·비구조 언어 공간이라 어마어마한 데이터가 필요.)

**아키텍처 함의**: *뭘 추천하나*는 추천 엔진이 풀고, LLM은 그 결과 + 사실(RAG) + 프로필을 받아 **"말로 엮는"** 역할. **취향 학습은 모델 가중치가 아니라 추천 엔진에서 일어난다.**

### 6-3. 그래서 규모 vs 제타 — 두 가지 교정

1. **같은 원리, 다른 엔진**: "쓸수록 개인화"라는 플라이휠 방향은 제타와 같지만, 제타는 RLHF로 가중치에 굽고 나는 추천 엔진을 행동 데이터로 굴린다. (원리 수준 O, 방법 수준 X)
2. **제타만큼 커야 강점이 생기는 게 아니다**: 추천 엔진은 RLHF보다 데이터 효율이 좋아 쓸 만한 우위가 훨씬 일찍 생긴다. 내 플라이휠 = *더 작은 베이스에서 더 빠르게 도는* 엔진. + 제타가 못 가진 **문화권 축**까지 있음.

## 7. 그냥 추천기가 아니다 — '여행 동반자'와 유대감

제품의 본질은 추천이 아니라 **동반자(유대감)**. 예: K-pop 콘서트 보러 온 팬에게 밥 한 끼도 "네 최애가 자주 가는 라멘집"으로 안내하며 *그걸 좋아하는 마음에 공감*하는 캐릭터.

### 7-1. 핵심 — 내 유대감은 제타와 종류가 다르고, 그게 유리하다

- 제타의 유대감 = **그라운딩 없음.** 외부 현실에 닻이 없는 순수 롤플레이 → 대화를 매력적으로 만드는 게 오직 *학습된 미감* → RLHF로 수백만 신호를 가중치에 구워야 함.
- 내 동반자 = **그라운딩 있음.** "얘가 날 이해하네"의 정체가 추상적 미감이 아니라 **이 사람이 사랑하는 그 구체적 사실을 안다**는 적중.
- ⇒ **구체성·적중은 RLHF가 아니라 데이터 + 검색 + 프레이밍에서 나온다.** 동반자 층을 넣어도 제타식 규모 싸움으로 안 끌려간다. 같은 데이터가 "추천"과 "유대감"을 동시에 먹인다.

### 7-2. 동반자 층의 2분할

- **페르소나/목소리**: 일관된 성격·톤. RLHF 규모 문제 아님 → 강한 베이스 + 페르소나 스펙(인플루언서 제공) + few-shot + 가벼운 SFT.
- **공감대/적중**: "네가 좋아하는 그걸 나도 알아." → 순수 데이터·검색 층 (라멘집 예시).

### 7-3. 방어력(moat)

- 범용 프런티어 모델은 따뜻하게 수다는 떨지만 *이 팬의 최애가 그 식당에 다녀갔다*는 사실은 모른다. → 그게 내 데이터고, 공감대의 진짜 원천.
- 대화 바닥선(여러 턴 따뜻·일관)은 분명히 필요하지만, 요즘 프런티어 베이스가 거의 공짜로 준다.
- **레버리지 최적 조합: 대화 바닥선은 강한 베이스(API)에서 받고, 유대감 차별화는 내 데이터로.**

## 8. 통합 아키텍처 — 한 캐릭터를 이루는 층들

### 8-1. 최종 모델 (검증된 멘탈모델 + 3가지 교정)

**감성 층 + 지식 층을 분리하고, 지식은 가중치 밖(검색)에 둔다** — 이게 현대 아키텍처의 정석. 이유: 사실은 변하니까(폐업·근황) 가중치에 구우면 안 되고, 페르소나는 잘 안 변하니 모델 쪽에 둬도 됨. 분리하면 지식을 갱신해도 성격이 안 망가지고, 성격을 다듬어도 사실이 안 깨진다.

**교정 3가지:**

1. **감성 능력은 캐릭터마다 0에서 키우는 게 아니다.** 감성·대화의 *바닥*은 캐릭터별이 아니라 **공유 자산(베이스 모델)**. 각 캐릭터는 그 위의 *얇은* 페르소나 층. → 새 캐릭터도 첫날부터 감성적으로 멀쩡(콜드스타트로 바보 시작 X). 캐릭터별 대화량이 키우는 건 "감성 바닥"이 아니라 **페르소나의 구체성·일관성**.
2. **"대화량 → 감성 향상"은 제타(자체 모델)의 동학.** 강한 베이스(API)를 쓰면 감성 바닥은 사 쓰는 거라, 내 대화량이 보상받는 곳은 **지식·개인화(추천) + 페르소나 다듬기**. ("양이 늘면 감성이 는다"는 내 구조에선 절반만 참.)
3. **"나눠서 학습"보다 "나눠서 각자 맞는 방법으로".** 페르소나/감성 = 가벼운 튜닝 or 프롬프트(가중치 쪽). 지식 = 학습이 아니라 **검색(가중치 밖)**. 지식을 모델에 학습시키려 하면 금방 낡고 환각이 생긴다.

### 8-2. 두 트랙 그림 (콘서트 예시)

```
                  ┌──────────────────────────────────────────┐
                  │       공유 감성 바닥 (베이스 모델)         │  ← 모든 캐릭터 공통, API가 거의 공짜로 제공
                  └──────────────────────────────────────────┘
                            ▲                        ▲
          ┌─────────────────┘                        └─────────────────┐
   [페르소나 트랙]                                            [지식·적중 트랙]
   이 캐릭터가 어떤 톤·말투로,                                  "네 최애가 다녀간 라멘집"
   얼마나 다정하게 말하나                                       = 행동 데이터 + 검색 + 추천
   = 베이스 + 페르소나 스펙(인플루언서) + few-shot               대화 쌓이면 → 취향 적중 ↑
   대화 쌓이면 → 일관성 ↑                                      (가중치 밖 = 검색, 학습 X)
          └─────────────────┐                        ┌─────────────────┘
                            ▼                        ▼
                  ┌──────────────────────────────────────────┐
                  │  한 응답에서 두 트랙이 만남 → "동반자" 1명 완성  │
                  └──────────────────────────────────────────┘
```

## 9. 네이티브 시티에 적용 — 정리된 설계 방향

- **베이스**: 강한 프런티어 모델(API)로 대화 바닥선 확보. 자체 모델 학습은 프라이버시·비용·통제가 절실해질 때 2층(LoRA/QLoRA)으로 내려가는 선택지로 **보류**.
- **페르소나**: 인플루언서/캐릭터별 페르소나 스펙 + few-shot. 필요 시 톤만 RLAIF/가벼운 SFT.
- **지식·추천**: RAG(사실) + 추천 엔진(취향) + 행동 데이터(누가 어디 가서 만족했나). 사실은 가중치 밖에 두고 항상 최신화.
- **데이터 루프**: 인플루언서 정답지 = 고품질 시드 + **eval 루브릭부터**. 트래픽 쌓이면 손님 암묵 신호로 보강 → (필요 시) DPO.
- **차별 축**: 문화권 × 관심사(팬덤 등)의 적중 = 제타가 못 가진 **그라운딩된 해자**.
